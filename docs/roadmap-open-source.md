# HubKit 开源公益迭代路线

HubKit 的目标是成为本地优先的个人自动化中控台。项目开源公益、非商业化，优先服务个人开发者、脚本作者和需要管理本地自动化任务的用户。

## 产品原则

- 本地优先：默认只服务本机，远程访问必须显式开启。
- 可解释：每个模块的运行状态、失败原因和修复建议都应该能被用户理解。
- 可恢复：配置修改、启动失败和危险操作都应该有回退路径。
- 低门槛：新模块接入不应该要求用户理解 HubKit 内部实现。
- 可维护：核心能力优先沉淀为稳定接口，实验能力不要污染生命周期主线。

## 三方评估结论

### 重度用户视角

痛点：
- Dashboard 已覆盖模块启停、日志、诊断、工作区雏形和高风险操作，但入口密度继续上升后，用户容易不知道“现在该看哪里”。
- 失败后的信息还需要继续压缩成可行动摘要，避免用户在日志、诊断、模块卡片之间反复跳转。
- 设置项同时包含即时生效、本地偏好、需保存配置和高风险动作，必须持续保持清晰标识，否则误操作成本会升高。
- 新用户最需要的是“把现有项目接进来并跑通”，不是先学习 HubKit 内部概念。

期望：
- 每个模块卡片都能回答 3 个问题：是否可用、为什么不可用、下一步怎么修。
- 工作区应该成为高频场景入口，例如“开发环境”“系统维护”“签到任务”，而不是单纯的模块分组。
- 日志中心需要从“文本查看器”升级为“问题定位入口”，自动带出最近失败和相关日志。
- 高风险动作要继续保留影响说明、回退路径和二次确认，不追求一步到位的危险快捷。

### 高级产品经理视角

定位：
- HubKit 是本地优先、开源公益、非商业化的个人自动化中控台。
- 核心价值不是“更多脚本功能”，而是把分散脚本变成可观察、可恢复、可编排的本地系统。

流程问题：
- 当前能力已经跨过单模块管理，下一阶段应围绕“接入 → 体检 → 运行 → 失败诊断 → 修复验证 → 编排复用”闭环收敛。
- 文档、CLI 和 Web Dashboard 必须使用同一套口径：`.hubkit.json`、`~/.hubkit`、`init-module`、本机默认绑定。
- 每个新能力都应该明确归类为核心主线、实验能力或本地偏好，避免 Dashboard 继续堆入口。

模块规划：
- 核心模块：配置、模块扫描、生命周期、日志、诊断、Web/API、安全确认。
- 增强模块：工作区编排、触发器、脚本工具箱、系统动作。
- 实验模块：特定站点签到、个人脚本模板、一次性自动化，必须通过配置或脚本包接入，不能污染核心协议。

### 高级全栈工程师视角

架构问题：
- `src/web/public/index.html` 仍承担样式、状态、渲染、API fallback、终端状态机和交互编排，理解成本高。
- `app-api.js` 已经形成 Web API client 的 seam，下一步应继续把请求/错误处理/响应归一化集中到这个 module。
- 高风险确认、WebSocket、Web 终端生命周期是脆弱路径，短期只加测试护栏，不做大迁移。
- 后端路由已经拆分出多个 route module，后续要继续保证 CLI、Web、scheduler 共享 lifecycle implementation，避免行为分叉。

工程期望：
- 每次拆分都必须带契约测试：导出 helper、inline fallback、action id、高风险 header、错误语义。
- 大日志、诊断、配置备份和工作区 API 要优先测试边界条件，避免本地工具在异常场景下放大风险。
- 安全默认值必须可测试：Web 默认绑定 `127.0.0.1`，敏感环境变量不出现在 Web/API 响应中。

## 迭代门禁

- 体验门禁：新增入口必须能说明用户任务、默认状态、失败反馈和回退路径。
- 产品门禁：新增能力必须归入接入、诊断、日志、工作区、安全边界或技术治理之一；商业化不进入路线。
- 工程门禁：新增 Web/API 能力必须有单元测试或契约测试覆盖，且通过 `npm test -- --runInBand`、`npm run build`、`git diff --check`。
- 安全门禁：远程访问、高风险操作、系统偏好修改、配置恢复、进程清理必须默认保守，并保留显式确认。

## 近期贡献验收清单

面向近期贡献者和并行 agent 的最小验收口径：

- 定位一致：改动必须服务个人本地自动化、开源公益和非商业化定位，不能引入付费分层、远程执行平台或商业增长入口。
- 用户闭环：新增或调整入口时，必须说明它处在“接入、体检、运行、失败诊断、修复验证、编排复用”哪一步，并保留默认状态、失败反馈和下一步动作。
- Local-first：Web、API、日志、配置和系统动作默认不扩大本机暴露面；远程访问、系统偏好、高风险操作和配置恢复必须继续显式确认。
- 可维护性：优先补测试或抽离纯展示 helper；不要把实验能力、站点特化逻辑或一次性脚本写进核心 lifecycle、scheduler 或模块协议主线。
- 协作边界：改动 `src/web/public/index.html` 前先确认是否可以落到 `app-api.js`、`app-log-renderer.js`、`app-formatters.js`、`app-diagnostics.js` 或 `app-workspace.js`；多个 agent 不同时编辑同一大文件。
- 验证要求：前端静态 helper 改动必须跑目标单测、全量单测、构建、`git diff --check`，并探测 `/` 与对应静态资源；纯文档治理至少跑 `git diff --check`。

## 近期主线

### Phase 0：可靠底座

目标：让现有功能可以长期维护，不再继续扩大脆弱面。

- 配置文件带 `configVersion`，为后续迁移留入口。
- 配置保存采用写入前备份和临时文件原子替换。
- Web 设置页区分“需保存”“即时生效”“本地偏好”“高风险操作”。
- API 和 Web 单文件逐步拆分，降低后续修改成本。
- 为设置页、配置管理、诊断结果补回归测试。

验收标准：
- 配置损坏或误改后有备份可恢复。
- 全量测试通过。
- 用户能明确知道设置项的生效范围。

### Phase 1：模块接入向导

目标：让一个已有 Node.js、Python 或 Shell 项目在 10 分钟内接入 HubKit。

- 新增模块接入向导。
- 生成 `.hubkit.json` 模板。
- 自动检测入口脚本、运行时、包管理器、Web 端口和常见环境文件。
- 接入前给出预检报告。
- 接入后自动进入模块体检。
- 接入文档统一使用 `node dist/cli/index.js init-module`，不再使用旧版 `module.json` 或 `~/.hub` 口径。

验收标准：
- 用户不手写 JSON 也能完成基础接入。
- 缺依赖、入口不存在、端口冲突等问题能在接入前暴露。

### Phase 2：诊断修复闭环

目标：失败后不仅知道哪里坏了，还知道下一步怎么修。

- 标准化体检 finding：影响、原因、建议、可执行修复动作、验证动作。
- 诊断页展示体检 finding 的影响、修复动作和验证动作。
- 体检结果按错误、告警、提示排序，并把最近一次启动失败纳入标准 finding。
- 对安全动作提供一键修复：重建 PID、打开日志、安装依赖、清理残留端口。
- 诊断页按错误优先排序。
- 模块卡片显示最近一次失败摘要。

验收标准：
- 常见启动失败不需要用户离开 HubKit 排查。
- 修复动作执行后能自动再次验证。

### Phase 3：日志中心

目标：让日志成为定位问题的入口，而不是最后才打开的文本。

- 跨模块搜索。
- 按级别、时间、模块、任务过滤。
- Dashboard 提供全局日志入口，后端 `/api/log-search` 可跨模块、脚本动作和系统动作按关键字与级别搜索最近日志。
- 日志 tail 读取，避免大文件整读。
- 模块日志、脚本工具箱日志和系统动作日志统一使用 tail 读取。
- 日志轮转，避免无限增长。
- 模块长期运行日志在重新打开写入前自动轮转并保留最近 3 份。
- 最近失败日志自动聚合到诊断页。
- 失败类体检 finding 携带脱敏后的最近相关日志片段。

验收标准：
- 大日志文件不会明显拖慢 Web Dashboard。
- 最近一次失败可以直接定位到相关日志片段。

### Phase 4：工作区与编排

目标：从单模块管理升级到场景级自动化。

- 工作区一键启动、停止、重启。
- 模块依赖 DAG。
- 启动延迟和失败中断策略。
- 定时任务显示下一次触发时间和最近触发结果。
- 模块列表 API 返回定时任务状态，设置页展示下次触发与最近执行结果。
- 支持文件变化、端口访问、本地 webhook 等触发器。

验收标准：
- 用户可以定义“开发环境”“系统维护”“签到任务”等工作区。
- 工作区启动顺序可解释，失败路径可恢复。

### Phase 5：配置回滚与安全边界

目标：让用户敢于修改和自动化。

- 配置 diff、备份、恢复。
- 设置页可查看最近配置备份并恢复，API 提供备份列表与指定备份恢复能力。
- 配置恢复前展示影响范围，覆盖模块目录、分组、自启、定时、启动策略、Web 入口和卡片显示差异。
- 高风险操作二次确认；配置恢复、强制关闭、全量关停、Web 终端停止、高风险脚本和系统启动偏好统一使用包含影响与回退路径的确认模板。
- 环境变量检查只显示缺失项，不暴露敏感值；Web/API 输出会隐藏完整变量清单，仅保留缺失项和数量。
- Web 服务默认绑定本机地址，远程访问需要显式配置。
- `node dist/cli/index.js web` 默认监听 `127.0.0.1`，远程访问需显式传 `--host`。

验收标准：
- 误改配置后可以从 HubKit 恢复。
- 默认部署不扩大本机安全暴露面。

## 技术治理

- 拆分 `src/web/public/index.html`：样式、状态、API client、渲染函数分离。
- 拆分 `src/web/api/routes.ts`：模块、设置、诊断、脚本工具箱、系统动作分路由。
- 建立统一 lifecycle 模块，让 CLI、Web、scheduler 共享同一套启动/停止逻辑。
- 将 `TaskScheduler` 从半实现推进为真实 adapter 驱动，或暂时从对外路径隐藏。
- 对配置、日志、模块扫描建立稳定测试面。

### 前端静态 Helper 分层

目标：继续降低 `src/web/public/index.html` 的维护成本，但不把高风险运行链路拆散。

已形成的分层：
- `app-api.js`：只放 Web API client、请求参数组装、响应解析和 fallback 对齐。
- `app-log-renderer.js`：只放日志行渲染、日志搜索结果渲染、日志过滤判断。
- `app-formatters.js`：只放展示文案、状态 class、摘要格式化、图标和颜色映射等纯展示 helper。
- `app-diagnostics.js`：只放诊断页纯数据判断，例如筛选、缺命令/缺变量判断、端口解析。
- `app-workspace.js`：只放工作区卡片、设置项、编辑器和模块列表的 view-model helper；不放启动/停止编排、API mutation 或运行时 lifecycle。
- `app-dashboard.js`：只放 Dashboard section 的纯数据组装，例如签到、工作区、模块分组、脚本工具箱和系统动作卡片归组；不放卡片渲染、API mutation、WebSocket 或高风险确认流程。
- `app-ui-prefs.js`：只放浏览器本地 UI 偏好的解析、默认值和数值边界归一化；不直接读写 `localStorage`、DOM 或主题状态。
- `app-settings.js`：只放设置页概览、配置风险计数、启动策略合并和模块排序等纯 view-model helper；不放保存设置、即时生效 API 或高风险恢复流程。

短期继续抽离的优先级：
- 优先抽离纯函数：输入完全来自参数，输出为字符串、布尔值、数组或简单对象。
- `index.html` 保留 thin wrapper，避免一次性改动大量调用点。
- 每次抽离必须新增或扩展对应 `tests/unit/web-*.test.ts`，同时保护 script 加载顺序和 wrapper 转发。
- 新增静态 helper 后必须跑目标单测、全量单测、构建、`git diff --check`，并探测 `/` 与新增 helper 资源。

暂缓抽离的边界：
- 高风险确认、WebSocket、Web terminal lifecycle 只加测试护栏，不做结构迁移。
- 含全局状态写入、DOM 生命周期、定时器、终端 session、进程清理、配置恢复的函数不进入静态 helper。
- 设置页概览、工作区编排等依赖全局 `settings` 或运行时状态的函数，先通过测试固定行为，再评估是否引入小型 view-model helper。

下一批安全小步：
- 继续优先抽离 workspace/settings 的 view-model helper，例如卡片展示态、编辑器空态、输入控件 id、按钮 loading 状态和列表摘要。
- Dashboard 组装 helper 只接收已解析的 section 来源和格式化回调，`index.html` 继续注入全局状态并负责渲染分发。
- UI 偏好 helper 只处理纯数据归一化，`index.html` 继续负责读取/保存浏览器本地缓存和应用 CSS 变量。
- 设置页 helper 只接收 `modules`、`settings`、默认策略等快照，输出概览和排序结果；保存、恢复、即时 API 调用仍留在 `index.html`。
- 每个 helper 只接收参数，不直接读取 DOM、`localStorage`、WebSocket、终端 session 或高风险确认状态。
- `index.html` 保留 thin wrapper 注入全局状态，避免 helper 直接依赖页面级变量。
- 测试优先覆盖 helper 输出和 wrapper 转发，再覆盖模板中是否消费 view-model 字段。
- 若发现某个候选点需要写全局状态或触发 API，先停止抽离，只补测试护栏或拆出更小的纯数据部分。

### UI 模块规划落地顺序

近期 UI 模块化先服务高频个人自动化闭环，不追求一次性拆完整个 Dashboard：

- 第一优先：日志、诊断、工作区卡片的展示摘要和过滤状态。重度用户最先需要从卡片直接判断“哪里坏了、下一步做什么”，这些 helper 必须保持纯输入输出，优先补边界测试。
- 第二优先：设置页中需保存、即时生效、本地偏好和高风险动作的视觉分区。产品上先减少误操作和概念混杂，工程上只抽离文案、计数、空态和 view-model，不迁移保存或确认流程。
- 第三优先：模块接入向导的预检摘要、检测结果和失败建议。它直接服务开源新用户，但实现前必须先固定 CLI、Web 和文档口径，避免出现多套接入路径。
- 暂缓：WebSocket 状态机、Web terminal 生命周期、高风险确认弹层和 API mutation 编排。除非有明确 bug，只加契约测试和边界测试，不做结构拆分。
- 验收：每个 UI 模块小步都要能对应用户任务、产品阶段和工程 owner 文件；如果无法说明这三点，先回到路线文档或测试护栏，不进入实现。

并行协作规则：
- 优先派只读 explorer 扫描候选点、测试缺口和产品路线，不让多个 agent 同时编辑 `src/web/public/index.html`。
- 如果子 agent 因线程上限不可用，主线程只推进一个窄范围小步，并在最终说明里记录该限制。
- worker 需要写代码时必须先声明文件范围，避免与已有未提交改动或其他 agent 输出重叠。
- 前端 helper 改动的默认验证链保持为目标单测、全量单测、构建、`git diff --check` 和静态资源探测。
- 文档治理改动不要求启动 Web 服务，但必须至少通过 `git diff --check`。

## 不做什么

- 不做商业化付费分层。
- 不默认做远程执行平台。
- 不把实验模块直接塞进核心协议。
- 不用复杂分布式架构解决单机本地工具的问题。
- 不把 `install-launcher`、`install-service` 等未实现命令写成当前可用主流程。
